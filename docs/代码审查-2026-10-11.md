# MiniGameVote 代码审查（2026-10-11）

审查范围：`src/main/java/cn/shijiu/minigamevote/` 全部 13 个类 + `plugin.yml` + `config.toml`。
结论：**整体结构清楚、异步划分正确，但有 2 个会让功能静默失效的问题，已修。**

---

## 已修复

### 🔴 P0-1　HTTP 线程池自锁 —— 状态查询会全部超时

`HttpService` 里 `HttpClient` 和 `CompletableFuture.supplyAsync` 用了**同一个** 4 线程池：

```java
pool   = Executors.newFixedThreadPool(4, ...);
client = HttpClient.newBuilder().executor(pool).build();   // ← 问题在这
request = supplyAsync(() -> doRequest(...), pool);          // doRequest 阻塞在 send()
```

`HttpClient` 的 executor 是给它内部跑连接/读写用的。我们的任务正阻塞在 `send()` 上等结果，
两边抢同一个固定池子会互相饿死：线程全卡在 `send()`，内部任务没线程跑，请求只能等到超时。

**后果很隐蔽**：一次达标要并发查 6 个实例，全部超时 → `on-query-error = "idle"` 会把它当成"空闲"
→ 照常开服。**"已有小游戏在跑就作废"这条规则等于失效**，而且后台不会报错。

**修法**：不给 `HttpClient` 设 executor（用它自己的默认线程池），`supplyAsync` 仍用我们的池子；
池子从 4 加到 8（≥ 一次达标的并发数，否则请求要排队）。

**验证**：起本地 HTTP 服务并发打 8 个请求——
修复前进程直接卡死超时（SIGTERM），修复后 8/8 成功、105ms。做了对照实验确认不是假阳性。

### 🔴 P0-2　配置模板曾被改写成占位符

重排 `config.toml` 版式时，`url` 和 `daemon-id` 被覆盖成了 `http://mc.com` / `xxx`，
而服主本地那份还是真实值 —— 两份不一致，照错的那份上线必然连不上面板。

**后续处理**：仓库是公开的，`src/main/resources/config.toml` **必须**保持占位符，
真实面板地址 / 守护 uuid / 实例 uuid 只写在不入库的本地副本里。
首次接入用 `/votegameadmin test` 和 `/votegameadmin mcsm` 核对（接口从没真机测试过，只有文档依据）。

### 🟠 P1-1　异步回调抛异常 → 投票流程永久卡死

`VoteFlow.run()` 的 `whenComplete` 里直接 `futures.get(i).join()`，外面没有 try。
一旦抛异常，会被 `CompletableFuture` **悄悄吞掉**，`finish()` 不执行 →
`resolving` 永远停在 `true` → **之后所有达标都不再触发**，后台一条日志都没有，
只能靠 `/votegameadmin reload` 解锁。

**修法**：整个循环包 try/catch 记 WARNING；`open()` 的回调改成 `try/finally`，
保证任何路径下都解锁。

### 🟠 P1-2　uuid 重复时重复查询，且没有校验

`statusUrls()` 不去重。配置模板里 6 个游戏的 uuid 都是同一个占位值，服主没改全的话
会拿同一个假 uuid 查 6 次，全部失败 → 按 idle 处理 → 照样开服（又是静默失效）。

**修法**：
- `statusUrls()` 去重
- 新增 `Mcsm.looksLikeUuid()`（32 位十六进制），启动时对"多个游戏共用同一 uuid"
  和"uuid 不像 uuid"各打一条 WARNING

### 🟡 P2　reload 与进行中流程的竞态

HTTP 是异步的。`reload` 清空票数后，旧流程的回调才回来，会执行 `votes().reset()`
把 **reload 之后新投的票** 清掉。HTTP 慢（3s 超时）时概率不低。

**修法**：`MiniGameVote` 加配置代次 `generation`（reload 时 +1），
流程启动时记下代次，回主线程时比对，不一致就丢弃本轮结果（只解锁，不动票数）。

## 观察项（确认无害，未改）

| 位置 | 情况 | 判断 |
| --- | --- | --- |
| `Mcsm.isBusy()` | 每次调用都重建 `watched()` 集合 | 6 个实例无所谓，纯浪费，不改 |
| `plugin.yml` `api-version: 1.21` | 服务端是 26.2 | 只是声明，不影响加载 |
| `Json.parse()` | 不检查尾随内容，`{...}garbage` 也能过 | 面板响应不会这样，容错反而好 |
| `HttpClient` | 没有 close 方法 | 该类本就不需要关闭 |
| `HttpService.shutdown()` | `shutdownNow()` 会中断进行中的请求 | 只在插件禁用时发生，无所谓 |
| `VoteManager.votesOf()` | 非 synchronized 读 | 读的是 `AtomicInteger`，最多读瞬时值 |
| `VoteManager.remove()` | `decrementAndGet() <= 0` 时移除计数 | 与 `cast()` 同为 synchronized，无竞态 |
| `Toml` | 行尾注释按引号状态扫描 | 已修过（VTpa 的老坑），当前正确 |

## 写得对的地方（别在后续改动里弄丢）

- **环境变量取不到 → 置空，绝不保留 `${env:XXX}` 字面量**。宁可发空让服主立刻发现，
  也不能把占位符原样发给面板。这条是对的。
- **`data.status` 与顶层 `status:200` 严格区分**。顶层那个是 HTTP 状态码，
  拿它当实例状态会让"HTTP 成功"被读成"运行中"，判定全乱。已有注释 + 断言覆盖。
- **零依赖 JSON/TOML**。为读两个字段去依赖服务端里的 Gson，
  等于把插件存亡押在"服务端一定带某个库"上，本地也测不了。这个取舍是对的。
- **异步边界干净**：`request()` 在线程池，`whenComplete` 一律 `sync()` 回主线程再广播/改票数。
- **一人一票 + 退出丢票 + 播报范围**三者联动一致：退出后票没了，自然也不再收到播报。
